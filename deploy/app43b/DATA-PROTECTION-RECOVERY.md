# Data Protection persistence and recovery

## Implemented source contract
`PointOfSale.API/Configuration/ProductionDataProtection.cs` uses the explicit configuration value `DataProtection:ApplicationName` in SetApplicationName, an existing absolute `DataProtection:KeysPath`, PersistKeysToFileSystem,90-day key generation lifetime, RSA>=2048 active PEM certificate/private key, ProtectKeysWithCertificate and retained DecryptionCertificates/UnprotectKeysWithAnyCertificate. Current validity is required only for the active wrapping identity; expired retired identities remain usable. Certificates are owned/disposed with the DI container and private PKCS12 buffers are zeroed. No automatic key/decryptor deletion or certificate rotation exists.

Production now refuses an empty ring rather than silently generating a replacement, and Linux ring directories granting other-user access. The discriminator is never replaced by a guessed `PointOfSale` value. That is only a non-Production default, not legacy-production evidence.

## Backup and node-loss recovery
Existing B2-backed PostgreSQL/Mongo backup resources do not include/prove DP protection: no ring consumer existed. Existing off-host transport can be reused with an explicitly approved DP prefix/access/retention and uploader integration, but that integration, encryption-at-rest and restore coverage are **NOT VERIFIED**. Never assume a successful database backup contains ring or wrapping keys.

Prepared `validation/app43b/RecoveryTool`: AES-256-GCM archive with authenticated version context, supplied32-byte escrow-key **file reference**, random nonce, maximum bounded archive input, create-new archive, no overwrite/merge restore, path/type validation and0700/0600 Linux restore modes. It does not generate production escrow keys, upload B2, read wrapping keys or install a service. Run on an approved existing backup/recovery execution environment; availability of its .NET runtime/uploader must be established before scheduling. No new resident component is required or claimed already present.

Ordered procedure (separate approval):
1. Custodian verifies original ring/discriminator/decryptor inventory without exporting private bytes to evidence. Preserve an unchanged recovery copy and identify the approved off-host backup execution/transport.
2. Back up the certificate-wrapped ring with `dotnet RecoveryTool.dll backup APPROVED_RING NEW_ENCRYPTED_ARCHIVE ESCROW_KEY_FILE`. Store discriminator/config version and non-secret public-cert inventory with recovery metadata; escrow wrapping private keys and archive key independently under approved custodians. The ring archive alone cannot decrypt data.
3. Use the existing approved encrypted/authenticated off-host uploader and dedicated scoped prefix. Verify object hash/retention/readability and restore before first traffic; then schedule owner-approved intervals and backup after key changes.15-minute RPO/60-minute RTO are proposals, NOT achieved promises. Retention must cover the longest protected-data lifetime, not merely90days.
4. After node/disk loss, recover K3s/data dependencies through their existing approved runbooks, provision/bind a dedicated retained local RWO claim on the replacement single node, and restore the encrypted ring into a NEW isolated path using the escrow file. Recover original ApplicationName and all necessary wrapping identities separately. Apply root0700/UID1654 and read-only private mounts; never initialize a fresh ring.
5. In isolation, unprotect a custodian-retained synthetic legacy canary and compare non-secret metadata; validate ownership and latest backup coverage before a one-API Recreate cutover. Keep the prior ring/archive/decryptors unchanged for rollback. Replacement node name/affinity must match the approved profile.
